# The stateless Responses reconstruction GPT-5.6 tool traffic is rebuilt as

Recorded 2026-09-07 from vendor documentation.
**Live run: PENDING — operator ceremony** (see below).

`translate.ToResponses` (B5) rebuilds a Chat Completions conversation as a
`POST /v1/responses` request that is stateless (`store: false`) and carries
the tool round trip as `function_call` / `function_call_output` input items
correlated by `call_id` alone — no item `id`, and no `reasoning` items,
because modelgate never sees the encrypted reasoning that produced them.
B4–B8 are written around that shape. This record is what they cite.

## Documented contract

Item correlation:

> Tool calls and their outputs are two distinct types of Items that are
> correlated using a `call_id`.

— OpenAI, *Migrate to the Responses API*,
<https://developers.openai.com/api/docs/guides/migrate-to-responses>
(read 2026-09-07).

Storage:

> Responses are stored by default. Chat Completions are stored by default
> for new accounts. To disable storage in either API, set `store: false`.

— same page.

Item fields, from the API reference for `POST /v1/responses`
(<https://developers.openai.com/api/reference/resources/responses/methods/create>,
read 2026-09-07):

| Item | Required | Optional |
|---|---|---|
| `function_call` | `type`, `call_id` ("The unique ID of the function tool call generated by the model"), `name`, `arguments` | `id`, `status`, `async`, `caller`, `namespace` |
| `function_call_output` | `type`, `output` | `id`, `call_id`, `name`, `status`, `caller`, `namespace` |
| function tool | `type`, `name` | `description`, `parameters`, `strict`, and others |

So `id` is documented as optional on both items, and a function tool in
the Responses API is flat (`{"type":"function","name":…,"parameters":…}`),
not the Chat Completions `{"type":"function","function":{…}}` nesting.

`reasoning.effort` is model-dependent; the documented values are `none`,
`minimal`, `low`, `medium`, `high`, `xhigh` and `max`
(<https://developers.openai.com/api/docs/guides/reasoning>, read
2026-09-07). `xhigh` — the worker tier, five of seven agents — is in that
set, which the live run confirms for `gpt-5.6-luna` specifically.

## What the documentation does not settle

The reasoning guide's stateless advice is to replay everything the model
produced:

> To use `all_turns` with `store: false`, preserve every output item,
> append the next user message, and replay the complete history.

That is a recommendation for carrying reasoning forward. It does not say
whether a reconstruction that *omits* the reasoning items — the only kind
modelgate can build from a Chat Completions history — is accepted or
refused. A refusal would name the missing `reasoning` item or demand an
item `id` or `store: true`, and B5's input shape would have to change.
That is the load-bearing unknown, and the reason this probe exists rather
than a reading of the reference alone.

## The resolution this probe confirms

The brief gates B4 on this record. The controller's Stream B resolution
supersedes that: B4–B8 are written against the documented contract above,
and the live run is a confirmation step before the `v0.5.0` tag rather
than a gate on the code. It becomes load-bearing only if it contradicts
that contract — if OpenAI demands an item `id`, a `reasoning` item or
`store: true` — in which case B5's input shape is corrected before the
tag.
